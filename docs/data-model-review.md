# 数据结构审查（2026-07-31）

## 结论

当前结构已按“保单 → 方案 → 险种 → 责任”和“案件 → 票据 → 理算结果 → 台账”拆分，主干清楚，金额统一使用 `Decimal`，快照型理算结果与当前台账分离，适合审计和回滚。现有数据的孤儿关联及跨保单错绑检查均为 0。

主要风险不是范式，而是数据库未启用外键：`relationMode = "prisma"` 只让 Prisma 在客户端模拟关联，不会阻止脚本、运维 SQL 或并发请求写入孤儿数据。服务层已覆盖案件登记等核心校验，但无法完全替代数据库约束。

## 本次优化

- 案件分页由逐条加载改为批量加载。每页 20 条时，关联装载从约 80 次查询降为固定 4 次。
- 为案件的更新时间排序、状态加更新时间分页、人员事件筛选以及参数目录排序补充复合索引。
- 案件号和事件号生成改为 PostgreSQL 事务级 advisory lock，避免并发时“计数加一”生成重复编号。

## 关联评价

- `PolicyInsured` 作为保单与自然人的关联实体是合理的，可承载参保期间、方案和角色。
- `ClaimParty` 保存报案时快照而不是直接复用 `InsuredPerson` 是合理的，能保留当时身份、联系方式和收款信息。
- `ClaimCase` 同时保存 `policyId`、`policyInsuredId`、`insuredPersonId` 属于有意冗余，读取方便，但必须维持三者一致。
- `ClaimBillAmount` 和 `ClaimBillCustomValue` 支持纵向扩展，避免每增加一种金额或参数就改表；代价是类型约束与聚合查询更复杂。
- 理算结果保存责任、公式和表达式快照是合理的，不能只关联当前配置，否则历史结果会随配置变化。

## 后续建议

1. 在一次独立迁移中恢复数据库外键。先运行全量孤儿审计，再以 `NOT VALID` 创建并在线校验；删除策略默认 `RESTRICT`，案件内部明细可按明确生命周期选择 `CASCADE`。
2. 用复合外键或数据库触发器保证方案与保单、案件与参保关系、事件与被保人的跨列一致性。
3. 数据量达到十万级后，为姓名、申请人、证件号等 `contains`/不区分大小写查询评估 `pg_trgm` GIN 索引；当前小数据量不应提前承担其写入成本。
4. 给幂等记录和 LangGraph checkpoint 配置保留期与归档任务，防止只增不减。
5. 对理算提交增加并发版本或行锁测试，确保同一案件并发理算不会重复更新当前台账。
